# KDP Studio Library

A SaaS that generates print-ready puzzle/activity books for Amazon KDP. The
first generator is a "whodunit" logic-grid puzzle book — fully deterministic,
no AI involved, every puzzle mathematically verified to have exactly one
solution before it's ever rendered. Color-by-number and mystery-mosaic
generators follow the same pattern once this one is proven out.

## How it's structured

This is a pnpm monorepo:

```
apps/
  web/      Next.js app — marketing site, dashboard, API routes, auth, billing
  worker/   Background process that generates books (long-running, so it can't
            block or crash the web app)
packages/
  db/                       Prisma schema + client, shared by web and worker
  shared/                   Zod input schemas + KDP formatting constants
  generators/grid-mystery/  The deduction engine + PDF renderer for this book type
```

**Why a separate worker.** Generating a book means solving a constraint
puzzle and laying out a PDF — too slow to do inside a web request, and if it
crashed inside the web server it would take the whole site down with it.
Instead, an API route just writes a `Book` + `GenerationJob` row to
Postgres; the worker polls for queued jobs, claims one at a time (safely,
even with multiple worker instances running), and processes it in
isolation. One failing job retries a few times and then gets marked
`FAILED` — it never crashes the worker process itself, and it can never
take the web app down.

**How the puzzle engine works** (`packages/generators/grid-mystery`):

1. Pick the solution first — a random permutation placing one suspect per
   row and per column of an N×N floor plan (rooms generated by recursive
   rectangular partitioning).
2. Derive every true fact about that solution (room, wall adjacency,
   landmark adjacency, relative position to other suspects, height rank).
3. Select one clue per suspect from those facts, escalating to more
   constraining clues when needed.
4. **Verify uniqueness with a brute-force solver** (`solve.ts`) before
   accepting the puzzle — it brute-force-checks every possible arrangement
   and only ships the puzzle if exactly one satisfies every clue. This is
   the actual "verified deduction engine": correctness is proven per
   puzzle, not hoped for.
5. Render the verified puzzle to a KDP-formatted PDF (grid diagram, suspect
   clue cards, answer key) with `pdf-lib`.

No LLM, no external API call, no per-book variable cost anywhere in this
pipeline — the only failure modes are bugs, not a third-party outage or
bill. **v1 supports grid sizes 6–8** across all three difficulties; this
range was chosen because it's benchmarked at 90/90 successful generations
(worst case ~16s, typical case under 1s) — see the comment above
`MAX_GRID_SIZE` in `generate.ts` for why larger sizes aren't supported yet.

## Security choices already baked in

- **No passwords are stored by us.** Clerk handles authentication entirely;
  we only store a reference to the Clerk user ID.
- **Every API route checks ownership.** Books are always queried/created
  scoped to the signed-in user's own database row — there's no path where
  one user's request can read or modify another user's data.
- **All user input is validated with Zod** before it touches the database or
  the generator (see `packages/shared/src/schemas`).
- **Webhooks verify signatures.** The Clerk webhook route checks an HMAC
  signature (via `svix`) before trusting anything in the request body —
  required because webhook endpoints are, by necessity, public.
- **Rate limiting** on book-creation requests (Upstash), so one user or bot
  can't spam the generation queue.
- **Solver node budget.** The uniqueness-verification solver is bounded (see
  `SolverBudgetExceededError` in `solve.ts`) so a pathological input can
  never hang the worker indefinitely.
- **Security headers** (HSTS, X-Frame-Options, etc.) applied to every
  response — see `apps/web/next.config.ts`.
- **Secrets never touch the repo.** Everything sensitive is an environment
  variable, listed (with blank values) in the `.env.example` files, and
  `.env*` is gitignored.
- **Dependabot** is configured to open PRs for vulnerable dependencies, and
  CI runs `pnpm audit` on every push.

## Design system

Monochrome, KDP-neutral palette defined as CSS custom properties in
`apps/web/src/app/globals.css`, with class-based light/dark mode (toggle in
`components/theme-toggle.tsx`, applied before first paint by an inline
script in `layout.tsx` to avoid a flash of the wrong theme). All pages are
mobile-first responsive.

`DATABASE_URL` is required to run anything, and the puzzle generator itself
needs no third-party account at all.

## Local development

```bash
pnpm install
cp apps/web/.env.example apps/web/.env.local      # fill in DATABASE_URL at minimum
cp apps/worker/.env.example apps/worker/.env
pnpm db:generate
pnpm --filter @kdp/db migrate                     # creates the tables
pnpm dev                                           # runs the web app
```

To run the worker locally (in a second terminal):

```bash
pnpm --filter @kdp/worker dev
```

## Everyday commands

```bash
pnpm lint        # ESLint
pnpm typecheck   # TypeScript across every package
pnpm test        # Vitest
pnpm build       # Production build of everything
```

CI (`.github/workflows/ci.yml`) runs all four on every push and pull request.

## Roadmap

1. ✅ Foundation — repo, database, auth, CI, security baseline
2. ✅ Verified grid-mystery deduction engine, working end-to-end for grid
   sizes 6–8 (all difficulties), wired through the worker to a generated PDF
3. Larger grid sizes (9+) — needs a smarter multi-clue selection algorithm,
   not just a bigger attempt budget (see the note in `generate.ts`)
4. Stripe subscriptions, so other people can sign up and pay
5. Additional generators (color-by-number, mystery mosaic) reusing the same
   worker/job/PDF-rendering pattern
